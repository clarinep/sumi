# Run performance benchmarks

This guide shows you how to run performance benchmarks, monitor rendering throughput, and analyze load test results for Sumi.

## Automated benchmarking workflow

Sumi includes an automated GitHub Actions benchmark workflow (`benchmark.yml`) triggered on `workflow_dispatch`.

The workflow executes the following steps:

1. Checks out the repository code.
2. Installs the Rust toolchain and `wrk` HTTP benchmarking tool.
3. Builds Sumi in release mode.
4. Generates synthetic WebP card images in a test directory using `gen.js`.
5. Launches the Sumi binary in the background.
6. Runs `wrk` with the `benchmark.lua` script against `http://127.0.0.1:8888`.

## Load test execution script

To test real-world rendering performance, benchmark requests must not repeat identical query parameters. Repeating parameters allows HTTP proxies or OS file caches to skew test results.

Sumi uses a custom Lua script (`benchmark.lua`) with `wrk`:

```lua
request = function()
    local left = cards[math.random(#cards)]
    local right = cards[math.random(#cards)]
    local left_print = math.random(1, 999)
    local right_print = math.random(1, 999)
    local path = string.format("/render/drop?left=%s&right=%s&left_print=%d&right_print=%d", 
        left, right, left_print, right_print)
    return wrk.format("GET", path)
end
```

Every HTTP request generated by `wrk` requests a randomized card pair and randomized print numbers. This forces Sumi to perform full canvas composition, font rasterization, and WebP encoding on every request.

## Performance metrics and expectations

Benchmark performance depends on available host CPU resources.

### Standard server performance

When tested with 100 concurrent connections over 30 seconds (`wrk -t4 -c100 -d30s`):

* **Throughput:** 30 to 70 completed image renders per second.
* **Latency:** 120 to 300 milliseconds per request under active concurrency.
* **Payload size:** 350 to 400 KB per generated WebP response.

### High concurrency behavior

When incoming request rates exceed CPU capacity:

1. The CPU semaphore queues pending tasks up to the available core limit.
2. Requests waiting longer than 5 seconds in the queue drop automatically with an HTTP 429 status code.
3. Dropping stale queued requests prevents memory buildup and guarantees that active rendering tasks complete without crashing the server.

## Run benchmarks locally

To run performance benchmarks on your local machine:

1. Install `wrk`:
   ```sh
   sudo apt-get install wrk   # Ubuntu or Debian
   brew install wrk           # macOS
   ```

2. Build Sumi in release mode:
   ```sh
   cargo build --release
   ```

3. Generate test card assets or point `CARDS_DIR` to a directory containing `.webp` files:
   ```sh
   node gen.js
   ```

4. Start the Sumi server:
   ```sh
   CARDS_DIR=assets/cards PORT=8888 ./target/release/sumi
   ```

5. In a separate terminal window, run `wrk` with the benchmark script:
   ```sh
   wrk -t4 -c100 -d30s -s benchmark.lua http://127.0.0.1:8888
   ```

6. Inspect the terminal output for requests per second, latency percentiles, and HTTP status code distributions.
